# Windows and the native shell

[Architecture index](README.md)

Implementation notes for people changing Nile: Window configuration, frames, multiple and owned windows, popups, dialogs, menus, tooltips, translucent windows and platform chrome. Each note says where the code is and which trap it avoids. They are kept as written while the code was built, so check a name against the source before relying on it.

- Window: `nile-engine/src/window.rs` parses the root `<html>`'s `window-*` attributes (`WindowConfig`, verified against docs.sciter.com/docs/HTML/html-window) and `role="window-*"` (`role_at`). `App::resumed` builds the winit window from it; scripts and role buttons push `WindowCommand`s (nile-script) onto `View::window_requests`, which `App::sync_window` drains after every event and tick (it also follows `document.title` and publishes `View::window_rect` for `screenX`/`outerWidth`). Frameless windows resize via `edge_at` + `drag_resize_window` and drag via `Page::caption_press` + `drag_window`; both must run inside the mouse-press handler. Headless runs never create a window, so commands just queue.
- Native menu bar (macOS, Windows): `Window.this.menu = el` -> `N.menuSet` -> `View::app_menu`; `nile-engine/src/menus.rs` turns the `<menu>` markup into plain `MenuItem`/`Accel` data (`Page::app_menu`), runs a chosen item (`menu_click`: `role` -> `menu_role` (clipboard/edit roles send the key chord, window roles are returned to the shell), else a `click` event) and matches shortcuts for platforms whose menu doesn't (`menu_accelerator`, called from `default_key`). The shell (`nile-shell/src/menu.rs`, `app.rs::sync_menu`) rebuilds the native bar only when the model changes: macOS builds an `NSMenu` through `objc2-app-kit` (a `NileMenuTarget` class posts `UserEvent::Menu(tag)`, tag = node id or a negative standard action; App/Edit/Window menus added around the page's; one app-wide bar from the focused window); Windows uses `CreateMenu`/`SetMenu` per window with `WM_COMMAND` read in winit's message hook (`UserEvent::MenuIn`), written without a Windows compiler to hand (CI compiles it; its clippy/test/build steps print failures as annotations since raw logs need admin rights). On Linux (no system bar; `View::native_menu` false, `NILE_MENU=inline` forces it) `Window.this.menu` draws an in-window bar from the same markup (`renderMenuBar` in web.js; `.nile-menubar`/`.nile-menu` UA rules; choices come back through `N.menuInvoke` -> `View::menu_invocations` -> `menu_click`). C hosts: `nile_view_menu` (JSON from `menus::menu_json`), `nile_view_menu_click`, `nile_view_menu_accelerator`. No real menu has been clicked by a script here: macOS blocks System Events scripting.
- Frames (`nile-engine/src/frames.rs`): `<frame>` (block) and `<iframe>` (inline-block) get a UA default size; the outer layout only sizes the box. `Page::update_frames` (cheap without frames: it rescans only when `Document::version` changes) loads a nested `Page` per element into `Page::frames` (`Rc<RefCell<Frames>>`, shared with the script functions), from `src` or `srcdoc` (what `loadHtml` sets; `nile-base` holds its base folder), refreshes its content-box rect, and emits `newdocument`/`complete`. `Page::paint` draws each nested page into a buffer and composites it over the rect (after everything else, so outer menus/fixed boxes can't cover it). Input is routed in `Page::{pointer_moved, press, release, wheel, key, default_key, insert_text, ime_*, cursor, take_file_request, tick}`: a press focuses and captures the frame under the pointer, keys go to the focused frame, a wheel the frame can't use falls through to the outer page; `with_frame` lends the outer clipboard and modifiers. The HTML parser drops `<frame>` outside a frameset, so `nile-dom` rewrites it to `<nile-frame>` (and back in `convert`). Scripts: `el.document` (a `FrameDocument` proxy: `$`, `$$`, `eval`, `call`, `title`), `url`, `loadFile`, `loadHtml`, `loadEmpty`, `frame` and `contentWindow` run code in the frame's own script context through the `__frameEval` host function (JSON in/out, so only plain data crosses); `frame.postMessage(data)` and `window.parent.postMessage(data)` are queued (`Frames::posts`, `FrameSlot::outbox`) and delivered by `Page::deliver_frame_messages` (called from `sync`/`tick`) as a `message` event with `data`/`source`. A frame follows its containers: `FrameSlot::{map, origin, size, clip}` come from `LayoutTree::placement_of` (the box's transform incl. ancestors' scroll, and their clip); hit testing and `local()` go through the inverse, painting concats the matrix and clips (`examples/frames-transformed.html`; inside a `page-view: paged` sheet the sheet mapping isn't applied). Frame pages are never borrowed while their own scripts call back out, which is why the bridge is queues plus `try_borrow_mut`.
- Windows: the windowed shell is `nile-shell/src/app.rs`: a `Win` per OS window (winit window, softbuffer surface, `Page`, input state) in `App::wins`. Scripts' `new Window()`/`modal({...})` call `N.windowOpen`, which allocates an id (`nile_script::next_window_id`) and queues `WindowCommand::Open(WindowSpec)` on the opener's `View::window_requests`; `Win::sync_window` turns the requests that need other windows into `Action`s and `App::run` carries them out (create a window from `WindowSpec` fields, deliver `Post`, `close`, focus). `Page::load_window`/`html_window` take a `WindowInfo` (id, opener, modal, `parameters`) that scripts read through `N.windowInfo` (kept across reload in `View::window_info`); the first window gets its id in `main()` before its scripts run. `App::close` asks `Page::close_request` (the `closerequest` event, vetoable), closes children, tells the opener (`Page::window_closed` resolves `Window.closed`/the modal Promise) and exits when the first window closes; `blocked()` drops pointer/keyboard events for a window with an open modal child. Messages: `Page::window_message` fires `message` (`__windowMessage`). `Window.share` is JSON in a thread-local in `nile-script`. C hosts get the same through `nile_view_take_window_request` (JSON: open/post/close/focus/quit, left in the queue by `nile_view_take_window_command`), `nile_view_create_window`, `nile_view_window_message`, `nile_view_window_closed`, `nile_view_close_request`, `nile_view_window_id`; the first view of a host gets its own id from `next_window_id` too.
- Owned windows: `App::create` computes an `owner` (the `parent` field, else the opener for `modal`/dialog/tool/popup types); macOS calls `NSWindow addChildWindow:ordered:` through `objc2-app-kit` (`attach_to_owner`), Windows passes `with_owner_window` (`owner_hwnd`, written without a Windows compiler to hand: check it in CI), other platforms stay independent.
- Popups in their own OS windows ("portals"): `popup({window: "popup"})`/`takeOff({window})`/`Window.this.popupWindows` mark the popup (still a fixed-position element of the *owner's* page) with `N.portalSet(id, rect)` -> `View::portals` (`nile_engine::Portal`). `Page::paint` skips those boxes (`Overlay::skip`) and `Page::paint_portal(.., node, origin)` paints just the element's subtree (`Overlay::only`, `LayoutTree::subtree_range`) with the page point `origin` at the buffer corner. The shell's `sync_portals` makes a frameless always-on-top inactive winit window per portal; `portal_event` turns its pointer events into the owner's coordinates (`rect` origin + position) and forwards presses, wheel and keys to the owner's `Win::handle`. The page keeps its own viewport size, so hit testing outside the window just works.
- Dialogs: `nile-engine/src/dialogs.rs` has the `Dialogs` trait (open/save/folder/message) the embedder sets with `Page::set_dialogs` (stored in `View::dialogs`, inherited by frames and kept across reload); `Env::dialog` calls it with no `View` borrow held (it blocks) and the script native `N.dialog(kind, a, b, c, d)` returns `undefined` when there is none. The shell's `NativeDialogs` (`nile-shell/src/dialogs.rs`) calls the Win32 common dialogs directly on Windows (`win` module: `GetOpenFileNameW`/`GetSaveFileNameW`/`SHBrowseForFolderW`/`MessageBoxW`, owned by `GetActiveWindow()` so the parent is disabled while one is open; written without a Windows compiler, CI checks it; the shell functions are declared by hand because windows-sys 0.52 gates them behind a feature it lacks) and shells out to `osascript` / `zenity` then `kdialog` elsewhere; `<input type=file>` uses the same code. `Window` (`web.js`) mirrors docs.sciter.com/docs/DOM/Window: `Window.this`, `selectFile`, `selectFolder`, `modal(JSX message box)` (`new Window` throws). After editing AppleScript run it through `osacompile -e` to check syntax: a bad script fails silently as "cancelled".
- Inline message boxes (`web.js` `inlineBox`, UA `.nile-modal`/`.nile-messagebox*` rules): opt-in with an `inline` attribute or `Window.this.messageBoxes = "inline"`; plain elements in a fixed backdrop, custom `<button>` children, resolves a Promise (it cannot block QuickJS, unlike the native box). Focused buttons now activate on Enter/Space (`Page::is_button` in `default_key`).
- Tooltips: `Page::tooltip_hover_changed` (from `refresh_hover`) arms `tooltip_due` (500 ms, `TOOLTIP_DELAY`), `tooltip_tick` (in `tick`) calls `__tooltipShow(id, x, y)` in `web.js` and `tooltip_hide` (press, key, wheel, hover change) calls `__tooltipHide`; the JS fires `tooltiprequest`, else shows the nearest `tooltip`/`title`. `popup-position`/`popup-animation` are `ComputedStyle::{popup_position, popup_animation}` (text kept in `Declaration::raw`, which the cascade clears for everything but `popup-*`), read by `cssPopup`/`animateIn` in the popup code.
- Popups (`web.js`): `Element.prototype.popup`/`takeOff` lift an element to `position: fixed` with inline styles (saved and restored on close) at a spot computed from `anchorAt`/`popupAt` numpad points; `openPopups` + a capture `mousedown`/`keydown` listener dismiss them, `.nile-hover` is the menu highlight (no UA `:hover` rules: they'd make `state_deps.hover` true on every page). `Page::context_menu` (right click; `--rclick X,Y` headless) calls `__contextMenu`, which fires `contextmenu` and shows `evt.source` as a menu. `nile-dom` expands the `<tag.class>` shorthand (`<menu.context>`) before parsing (`expand_class_tags`).
- `<frameset cols|rows>` (+ `<splitter>`): `nile-dom` hides it from the HTML parser as `<nile-frameset>` (and closes `<splitter/>`); layout makes it a grid (`frameset_tracks`: `px`/`%`/`N*`/bare number per pane from the list, `SPLITTER` px per splitter child; any element is a pane). `Page::splitter_press`/`splitter_drag_to` (in `frames.rs`) resize by rewriting the `cols`/`rows` attribute (the dragged pane gets px, the pane after it too unless it is `*`), so the DOM stays the single source of truth; `el.frameset.state` reads pane sizes and sets the attribute. A frame's `content-style` CSS file is appended to the nested document as a final `<style>`. `html { height: 100% }` now resolves against the viewport (layout gives the root element a definite px height and extends `content_height` over the content, since the root no longer grows).
- Translucent windows: `WindowConfig::{material, translucent()}` (`window-frame=transparent` or `window-material`); `Page::canvas_background` keeps the root background's alpha for them (clear colour, unpremultiplied) and is white-composited otherwise. The shell's `present()` (app.rs) configures softbuffer's alpha mode (`Premultiplied`, else `Postmultiplied` with an `unpremultiply` pass (macOS), else `Ignored`, else `Opaque`) and copies rows when the platform pads them; softbuffer is a *pinned git rev* because 0.4.8 has no `AlphaMode` (move to 0.5 when released; even master supports alpha only on macOS/web). `nile-shell/src/material.rs` applies the material after window creation: an `NSVisualEffectView` placed below the content view in its superview (the page layer paints under its own subviews), winit's `set_system_backdrop` on Windows, `set_blur` elsewhere. `Window.this.material` just sets the root's `window-material` attribute; `sync_window` notices a change against `WindowConfig::from_document` and calls `material::apply` again (macOS removes the old effect view first). Windows draws translucent windows with `alpha_win::Presenter` (BITMAPV5 DIB with an alpha mask + BitBlt, type-checked for the msvc target in a scratch crate); Wayland gets ARGB from softbuffer. macOS transparency confirmed by the user (`examples/transparent.html`); the material view is not yet; Windows/Linux alpha is unimplemented in softbuffer.
- `Material::Auto` (the default when `window-material` is absent) vs `Material::None` (`none`): `material::effective(config)` turns Auto into Mica for a Native/Extended frame on Windows (title bar tint like Explorer/Sciter; needs build 22523+, older systems ignore it) and into nothing elsewhere; `apply(window, material, translucent)` only makes the window transparent when the page asked for a material or transparent frame (`translucent()` excludes Auto/None).
- Snap Layouts (`nile-shell/src/snap_win.rs`, Windows only, type-checked for the msvc target in a scratch crate): `install(hwnd)` subclasses a frameless window (`SetWindowSubclass`); `App::sync_window` publishes `Page::maximize_button_rect` (the first `role=window-maximize` element, physical px) with `set_rect`; the subclass answers `WM_NCHITTEST` over it with `HTMAXBUTTON`, asks for `WM_NCMOUSELEAVE` (`TME_NONCLIENT`), reports hover through `set_notify` -> `UserEvent::Snap` (the App moves the page's pointer to the button's centre, so `:hover` works) and turns a non-client left-button release into `SC_MAXIMIZE`/`SC_RESTORE`. Not yet for `window-frame=extended` on Windows (which is still a normal frame there).
- Window corners: `Page::window_corner_radius` (root `<html>`'s `border_radius.tl`, via `StyleMap::try_get`); `App::corner_radius` (0 when maximized/fullscreen or framed) is compared with a `Win::corner` stamp (radius, outer size, scale) in `sync_window` and `material::set_corner` applies it: Windows `SetWindowRgn` with `CreateRoundRectRgn` (type-checked in a scratch crate), macOS `setCornerRadius`/`masksToBounds` on the content view's layer and the effect views (`macos_corner`, written blind: check by eye). `material::apply` takes the radius so a recreated effect view is rounded too.
- `Frame::SolidShadow` (`window-frame=solid-with-shadow`, `WindowConfig::shadow()`): `App::create` passes it to winit's `with_has_shadow` (macOS; frameless windows otherwise get none) and `with_undecorated_shadow` (Windows, uncompiled here: CI). Linux leaves shadows to the compositor.
- App icon: `assets/icon.html` (CSS drawn, rendered by Nile: `nile assets/icon.html --png assets/icon.png --width 512 --height 512 --scale 2`; `icon-512.png` is embedded as `bundle::DEFAULT_ICON`, the window icon fallback in `App::create` and the icon `--pack` gives a bundle/.exe without `--icon`; `nile --brand` stamps icon + version into a Windows exe for the release workflow). The `font` shorthand is expanded by `expand_font` (style/size/line-height/family; font-size is applied first), and `overflow` clipping with `border-radius` is a rounded clip in the renderer's scroll-box branch.
