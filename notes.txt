Implement a native extension system for Nile, with SQLite as the first working extension.

First inspect the current repository, its instructions, application lifecycle, host-function bridge, module resolver, event-loop wake mechanism, packaging and tests. Adapt this design to the actual implementation. Do not assume APIs from earlier discussions already exist.

Goal

Allow a Nile application to import a separately distributed native capability:

```js
import sqlite from "@sqlite";

const db = await sqlite.open("app.db");

await db.execute(
    "CREATE TABLE IF NOT EXISTS customers (id INTEGER PRIMARY KEY, name TEXT)"
);

await db.execute(
    "INSERT INTO customers (name) VALUES (?)",
    ["Hamid"]
);

const rows = await db.query(
    "SELECT id, name FROM customers WHERE name = ?",
    ["Hamid"]
);

await db.close();
```

SQLite must remain outside Nile’s engine. Future extensions, including MySQL, should use the same public extension SDK.

Scope and concurrent work

I am independently working on HTML/CSS/JS compatibility. Keep your changes focused on extensions, their necessary runtime integration, documentation and examples.

Do not refactor or fix unrelated layout, styling, rendering, controls or DOM compatibility. Preserve concurrent changes. Prefer new modules and small integration patches in shared files.

Preserve existing public APIs. Do not change existing synchronous host functions into asynchronous functions.

1. Stable native extension ABI

Create a small public extension SDK, preferably as a dedicated crate with a generated C header.

Use a C ABI with one known initialization symbol:

```c
NileStatus nile_extension_init(
    const NileExtensionApi *api,
    NileExtension *extension
);
```

Adjust the precise signature if needed to establish clear ownership.

Requirements:

- ABI version and structure-size fields for extensible API tables.
- Fixed-width types, explicit status codes and opaque handles.
- No Rust layouts, trait objects, QuickJS values or internal engine pointers crossing the boundary.
- Named operation registration and extension shutdown hooks.
- An application/context identifier and call identifier on dispatched work.
- Structured error codes and messages.
- JSON arguments/results initially, with a separate byte-buffer facility for binary data.
- Explicit string and buffer ownership, validity periods and release rules.
- Allocate and release memory on the same side of the ABI, including Windows.
- Completion functions must copy extension-owned data before returning, unless an explicit ownership-transfer contract says otherwise.
- Rust panics must never unwind across the ABI. Align release-build behavior with documented guarantees.
- Document callback threads, allowed reentrancy and the lifetime of the supplied API table.

Keep the ABI small. Do not expose database-specific concepts in the SDK.

2. Extension packages and discovery

Support a package containing:

```text
sqlite/
    extension.json
    index.js
    native/
        <platform-and-architecture>/<shared-library>
```

Define and document a minimal manifest containing package identity, version, required ABI, JavaScript entry point and platform-specific native library paths.

Define one canonical platform naming scheme, including Linux ABI distinctions where necessary. Fail clearly on unsupported targets; do not guess a binary.

Let applications explicitly map an import name to a package:

```json
{
  "extensions": {
    "@sqlite": "./extensions/sqlite"
  }
}
```

Integrate with existing application configuration if available; otherwise introduce the smallest clear configuration mechanism.

Requirements:

- Resolve configured paths relative to the application configuration.
- Initialize declared native extensions before application startup scripts run.
- Resolve imports through the existing module loader.
- Avoid import-name collisions with Nile built-in modules.
- Load only declared native packages.
- Report missing libraries, symbols, unsupported ABI versions and invalid manifests clearly.
- Clean up partial initialization safely.
- Keep libraries loaded until shutdown; hot reload/unloading is out of scope.
- Explain that native extensions have process-level privileges and are not sandboxed.

Support ordinary filesystem packages first. For packed applications, either implement a deliberate native-library extraction/loading strategy or return an explicit unsupported-configuration error and document it. Do not imply that an OS loader can load a shared library directly from an embedded archive.

3. JavaScript wrappers

Keep native operations separate from the public JavaScript interface.

SQLite can register internal operations such as:

```text
sqlite.open
sqlite.execute
sqlite.query
sqlite.close
```

Its JavaScript entry point should wrap these into connection objects.

Provide a scoped internal bridge that wrappers can use without exposing pointers or unrestricted native-library loading.

Integrate ordinary ES-module imports. Do not require npm resolution or change Nile’s existing JSX behavior.

4. Asynchronous dispatch and event-loop integration

Database work must not block the UI thread.

Reuse the existing asynchronous application/host-call infrastructure where it fits. If essential pieces are missing, add the smallest reusable mechanism and document it.

Requirements:

- Calls return JavaScript Promises.
- Every call has a unique identity within its owning runtime/context.
- Extensions can resolve or reject from worker threads.
- Completion wakes the application event loop.
- All QuickJS interaction happens on the owning UI/runtime thread.
- Define the point at which a completion is accepted; duplicate completions are rejected.
- A closed context invalidates its pending calls.
- Late completion returns an error without dereferencing destroyed state.
- Synchronous native dispatch errors reject the Promise.
- Runtime/module reload cannot deliver old results to a new context.
- Define bounded queues or another explicit overload policy.
- Headless and custom-host operation remains possible through the engine’s tick/completion mechanism.

For SQLite, use a worker that owns the connection and executes its operations in order. Do not assume SQLite connections may be used from arbitrary threads.

5. Managed resources

Implement opaque resource handles scoped to the owning extension and script context.

Validate ownership and handle generation so stale or cross-context handles cannot access another resource.

Define:

- Explicit close behavior.
- Repeated close behavior.
- Calls after close.
- Ordering between queued queries and close.
- Cleanup on context destruction.
- Cleanup after partial failures.

Use explicit close plus context cleanup. JavaScript garbage collection must not be the only cleanup mechanism.

6. SQLite extension

Implement SQLite as an independent shared-library package using only the public extension SDK.

It may live in this repository for development, but must also be buildable separately against the SDK. It must not depend on Nile’s engine, shell or QuickJS internals, and the engine must not acquire a SQLite dependency.

Implement:

- `open(path, options?)`
- `execute(sql, params?)`
- `query(sql, params?)`
- `close()`

Requirements:

- Prepared statements and bound parameters.
- Define whether each operation accepts exactly one statement; reject unsupported multi-statement input explicitly.
- Ordered execution per connection.
- Explicit SQL NULL mapping.
- A lossless policy for 64-bit integers outside JavaScript’s safe integer range.
- Blob round trips through the SDK’s byte-buffer facility.
- Defined handling of duplicate result-column names.
- Useful database errors with stable extension error codes.
- Defined relative-path resolution, independent of incidental process working-directory changes.
- A documented transaction approach. Explicit BEGIN/COMMIT/ROLLBACK is sufficient initially; do not introduce a callback-based transaction helper with unsafe interleaving.

Do not implement MySQL yet. Document how another database extension would register operations and use the same resource/completion facilities.

7. Lifecycle and shutdown

Define and implement a shutdown sequence that:

- Stops accepting new extension work.
- Invalidates or settles pending JavaScript calls appropriately.
- Requests worker cancellation where supported.
- Closes extension resources.
- Joins workers and prevents further completions.
- Releases runtime, extension state and library handles in a safe order.

Distinguish cancelling a Promise from interrupting database execution. Do not claim native work is cancelled merely because its JS context closed.

Never unload code while callbacks or workers may still execute it. Avoid indefinite shutdown where a supported interruption mechanism exists; document remaining blocking cases.

Library paths must return errors rather than terminating the host process.

Architectural requirement: general-purpose extensions

Build a general-purpose native extension platform for Nile. SQLite is the first independently implemented consumer and validation example; it must not shape the core around database concepts.

The same SDK must support future extensions for printing, cryptography, networking, filesystem access, audio, image processing, hardware devices and other native services without modifying Nile’s core for each extension.

The extension platform must provide these generic capabilities:

- Namespaced operation registration.
- Immediate and asynchronous results.
- Structured errors.
- JSON values and binary buffers.
- Managed opaque resources with ownership and cleanup.
- Extension-to-JavaScript events and subscriptions.
- Background execution with safe event-loop delivery.
- Cancellation requests, distinct from guaranteed cancellation.
- Context initialization, disposal and application shutdown.
- Versioned ABI and explicit capability negotiation.

Support both request/response operations and ongoing event sources. Examples include a printer-status subscription, serial-device input, filesystem watcher or audio playback notifications. Events must target an owning context, use bounded queues with a documented overflow policy, and stop safely after unsubscribe or context disposal.

Do not force every extension to use a dedicated worker thread. Extensions may use their own worker, pool or asynchronous runtime, provided they obey the SDK’s threading and completion contracts. SQLite’s ordered connection worker belongs in the SQLite extension.

Keep the native SDK independent of JavaScript-specific implementation details. JavaScript wrapper modules provide the public classes and convenience APIs; extensions must never receive QuickJS pointers.

Separate the generic platform from individual extension packages. Nile must not contain a built-in list of extension names or special-case SQLite operations, database handles, SQL errors or connection management.

Validate generality with two independent consumers:

1. A SQLite extension demonstrating asynchronous operations, binary data and managed resources.
2. A small non-database fixture demonstrating an event subscription, background notifications, unsubscribe and cleanup.

Do not build speculative universal APIs. Rendering integration, hard real-time callbacks and other capabilities that need additional contracts may require future versioned SDK additions. Clearly document those boundaries rather than claiming the initial ABI supports every possible extension.


Implement native-extension support for packed Nile applications.

Inspect the current packer, virtual filesystem, extension loader, configuration discovery and tests first. Preserve concurrent changes and keep this work separate from unrelated HTML/CSS/JS compatibility improvements.

Goal

The same application and extension package must work unpacked and packed:

import sqlite from "@sqlite";

Do not change the public extension ABI or require extension-specific engine code. SQLite and notifications are validation examples; the solution must support any compatible extension.

Architecture

Separate:
1. Reading package manifests and JavaScript from filesystem or packed assets.
2. Materializing native files onto the real filesystem.
3. Loading verified native paths through the existing extension host.

Keep JavaScript wrappers and ordinary assets inside the archive. Extract only native binaries and explicitly declared native dependencies.

Packing

- Discover the application’s declared extensions.
- Validate manifests, package containment and required files.
- Include wrappers, manifests and selected platform-native files.
- Support explicit target selection; reject missing target binaries.
- Record content hashes and the complete native file inventory.
- Support companion libraries/assets through a generic manifest declaration; do not hard-code SQLite.
- Reject malformed or ambiguous declarations before producing an executable.
- Retain existing filesystem-extension behavior.

Extraction cache

Use an OS-appropriate, user-private cache directory with a layout based on application identity and native package content hashes.

Requirements:
- Stream files from the archive with explicit extraction-size limits.
- Reject absolute paths, traversal, duplicate/conflicting destinations and escaping symlinks.
- Create staging directories securely.
- Verify file lengths and hashes before publishing.
- Handle simultaneous launches through locking and atomic publication.
- Reuse only verified cache entries; detect corruption and safely rebuild them.
- Avoid following pre-existing symlinks in cache paths.
- Load libraries by absolute path.
- Never overwrite or delete libraries belonging to a running application.
- Keep old-version cleanup conservative; omitting automatic cleanup initially is acceptable if documented.
- Do not fall back to arbitrary working-directory or system-library searches for the extension entry library.
- Treat hashes as integrity checks, not a substitute for signed distribution or protection against malicious same-user processes.

Dependencies and platforms

Preserve each package’s native directory layout and support declared companion dependencies.

Use appropriate platform mechanisms:
- Linux: extension dependencies should use suitable $ORIGIN-relative loader paths.
- macOS: preserve signed binaries and @loader_path/@rpath dependency arrangements.
- Windows: use a scoped dependency-search strategy that avoids unsafe process-wide search-path changes where practical.

Document build-time requirements and platform limitations. Do not claim extraction bypasses macOS signing, notarization or hardened-runtime requirements.

Also support real native files inside an application bundle or beside a packed executable through an explicit configuration mode. Do not silently discover arbitrary external plugins.

- Extracted native package paths.

Never make the extraction cache the default location for SQLite databases or user settings.

Define packed-app relative database-path behavior explicitly. Preserve existing unpacked semantics. If a stable application-data path API/configuration is needed, add the smallest general-purpose facility and document it.

Lifecycle and errors

- Keep materialized files available throughout the extension instance’s lifetime.
- Return structured startup errors identifying the package, target and failed operation.
